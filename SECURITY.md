# Security

Документ описывает модель безопасности HostMonitor: как аутентифицируются
агенты, как выдаются и ротируются ключи, что защищено и что остаётся на
ответственности администратора при развёртывании.

## 1. Модель угроз

Панель — доверенный узел. Агенты на нодах и сеть между ними — потенциально
недоверенные. Защищаемся от:

- подделки метрик/логов/результатов команд от имени чужой ноды;
- кражи токена ноды из конфига (переход на Ed25519);
- перебора пароля администратора (rate-limit);
- фиксации сессии (regenerate + strict mode);
- выполнения произвольных команд на ноде по указанию скомпрометированной
  панели (allow-list на агенте);
- replay перехваченных запросов агента (timestamp ±60 с).

## 2. Аутентификация агентов (Ed25519)

Агент подписывает **каждый** запрос к панели:

```
signature = Ed25519_sign( SECRET_KEY,
    METHOD + "\n" + PATH + "\n" + TIMESTAMP + "\n" + BODY )
```

- `METHOD` — верхний регистр (`GET`, `POST`).
- `PATH` — `REQUEST_URI` как есть, включая query string.
- `TIMESTAMP` — unix-время в секундах.
- `BODY` — сырое тело запроса (для `GET` — пустое).

Заголовки: `X-Agent-Node-Id`, `X-Agent-Timestamp`, `X-Agent-Signature`
(base64 от 64 байт подписи; hex тоже принимается для отладки).

Проверка на панели — `monitoring/includes/agent_auth.php`
(`sodium_crypto_sign_verify_detached`). Отклонения окна ±`AGENT_AUTH_CLOCK_SKEW`
(по умолчанию 60 с) — replay.

### Scopes

Ноде выдаётся набор прав; опасные (`system:power`, `system:exec`,
`firewall:write`, `update:install`) **не выдаются по умолчанию**. Проверка —
`require_scope()`. Legacy-ноды (Bearer-токен) получают `legacy:full` и
проходят любую проверку — это временно, до полной миграции.

### Legacy Bearer (переходный период)

Пока в `node.conf` есть `NODE_TOKEN`, агент ходит с `Authorization: Bearer`.
Если в запросе присутствуют любые `X-Agent-*` заголовки, откат на Bearer
запрещён (`authenticate_agent()`), иначе подделкой заголовков можно было бы
уйти в legacy-ветку.

## 3. Enrollment (первичное подключение)

1. Админ в панели: **Ноды → «Подключить ноду (Enroll)»**.
2. Панель генерирует одноразовый код (8 символов, TTL 15 мин), в БД хранит
   только `sha256`.
3. На ноде: `install_agent.sh --enroll <КОД> --master https://panel/` →
   `agent/enroll.py` обменивает код на пару Ed25519.
4. Панель сохраняет только **публичный** ключ (`nodes.public_key`). Приватный
   seed отдаётся ровно один раз и записывается в `node.conf`
   (`NODE_SECRET_B64`); токен (`NODE_TOKEN`) при этом не нужен.

`node.conf` содержит секрет — права `640` и владелец сервисного пользователя.

## 4. Ротация и восстановление ключей

- Ротация: `GET /api/nodes.php?id=N&action=rotate-key` (только админ). Новый
  seed отдаётся один раз; событие пишется в `key_rotation_log`.
- В `nodes` хранится только публичный ключ, поэтому компрометация панели не
  раскрывает приватные ключи нод.
- Потеря `node.conf` на ноде — повторный enroll (новый код) для той же ноды.

## 5. Команды нодам

- Канал команд — pull-модель (`GET /api/nodes.php?action=get-command`).
- Агент исполняет только команды из allow-list
  (`agent/commands.py`, default-deny); неизвестная команда отклоняется с
  причиной, которая уходит в панель.
- Опасные действия требуют явного флага на ноде:
  - `ALLOW_DANGEROUS_COMMANDS=true` — `reboot`, `shutdown`, `kill`, `restart`,
    `firewall`;
  - `ALLOW_AGENT_UPDATES=true` (по умолчанию) — самообновление агента.
- Панель ставит команды только из админской сессии (`nodes_require_admin()`).

## 6. Сессии и вход

- Cookie: `HttpOnly`, `SameSite=Lax`, `use_only_cookies`, `use_strict_mode`.
- При успешном входе — `session_regenerate_id(true)`.
- 2FA (TOTP) с кодами восстановления и «доверенными устройствами».
- Rate-limit: 5 неудач / 15 мин **по IP** (`data/login_attempts.json`) и
  **по username** (`login_attempts`). При успехе счётчики сбрасываются.
  Отсутствие таблицы `login_attempts` не ломает вход — остаётся IP-лимит.

## 7. Развёртывание

- Каталог `monitoring/data/` (конфиг БД, логи попыток) закрыт на уровне
  веб-сервера (`nginx/monitoring.conf`: `location ^~ /data/ { deny all; }`).
- Панель и агент должны использовать HTTPS; на HTTP приватность трафика не
  гарантируется. Для HTTP-панели установщик ставит `TLS_VERIFY=false` только
  осознанно — для `https://` проверка сертификата остаётся включённой.
- Рекомендуется ограничить доступ к панели (VPN/офисные сети) и выдать
  администратору сильный пароль + 2FA.

## 8. Что НЕ защищено

- Скомпрометированный администратор/панель может отдать ноде любую команду
  из allow-list. Разрушительные последствия ограничены флагами
  `ALLOW_DANGEROUS_COMMANDS`.
- Компрометация `node.conf` (seed) позволяет действовать от имени ноды —
  до `rotate-key`. Следите за правами файла и не копируйте его в репозиторий.
- Sudo-правила агента (reboot/iptables/ufw/apt) — это расширение его прав;
  устанавливайте их осознанно.
