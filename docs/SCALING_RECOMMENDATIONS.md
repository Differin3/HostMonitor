# Рекомендации по масштабированию системы мониторинга

## Текущая оценка производительности

### При COLLECT_INTERVAL=60 секунд (по умолчанию)

**Адекватная работа: 50-100 нод**
- При стандартной нагрузке (100 процессов, 50 контейнеров на ноду)
- При использовании MySQL на SSD
- ~9 записей/сек на ноду = ~450-900 записей/сек общая нагрузка

**Работа с замедлениями: 100-200 нод**
- Возможны задержки при очистке логов
- Медленные запросы при большом объеме данных
- ~900-1800 записей/сек общая нагрузка

**Требуется оптимизация: 200+ нод**

### При COLLECT_INTERVAL=15 секунд

**⚠️ ВНИМАНИЕ: Высокая нагрузка!**

**Адекватная работа: 20-30 нод**
- ~36 записей/сек на ноду = ~720-1080 записей/сек общая нагрузка
- Нагрузка в 4 раза выше чем при 60 секундах
- Рекомендуется только для критичных систем

**Работа с замедлениями: 30-50 нод**
- ~1080-1800 записей/сек общая нагрузка
- Возможны блокировки таблиц
- Медленная очистка логов

**Критично: 50+ нод**
- >1800 записей/сек - требуется оптимизация
- Высокий риск блокировок БД
- Не рекомендуется без партиционирования

### Расчет нагрузки на 1 ноду

**При 60 секундах:**
- 1 цикл в минуту
- ~537 записей/минуту = ~9 записей/сек

**При 15 секундах:**
- 4 цикла в минуту
- ~2148 записей/минуту = ~36 записей/сек (в 4 раза больше!)

**При 30 секундах:**
- 2 цикла в минуту
- ~1074 записей/минуту = ~18 записей/сек

## Узкие места

1. **DELETE + INSERT для processes/containers/ports**
   - Создает блокировки таблиц
   - Решение: использовать UPSERT (INSERT ... ON DUPLICATE KEY UPDATE)

2. **Одиночные INSERT в логи**
   - Нет батчинга
   - Решение: группировать INSERT в транзакции по 100-500 записей

3. **limitLogsCount()**
   - COUNT(*) на миллионах записей медленный
   - Решение: использовать приблизительный подсчет или партиционирование

4. **Отсутствие партиционирования**
   - Все данные в одной таблице
   - Решение: партиционирование по timestamp или node_id

## Рекомендации для масштабирования

### 1. Оптимизация INSERT операций

```sql
-- Использовать батчинг для логов
INSERT INTO process_logs (node_id, pid, process, level, message, timestamp) 
VALUES (?, ?, ?, ?, ?, ?), (?, ?, ?, ?, ?, ?), ...;

-- Использовать UPSERT для processes/containers
INSERT INTO processes (node_id, pid, name, cpu_percent, memory_percent, status) 
VALUES (?, ?, ?, ?, ?, ?)
ON DUPLICATE KEY UPDATE 
  name=VALUES(name), 
  cpu_percent=VALUES(cpu_percent),
  memory_percent=VALUES(memory_percent),
  status=VALUES(status);
```

### 2. Партиционирование таблиц логов

```sql
-- Партиционирование по месяцам
ALTER TABLE process_logs 
PARTITION BY RANGE (UNIX_TIMESTAMP(timestamp)) (
  PARTITION p202401 VALUES LESS THAN (UNIX_TIMESTAMP('2024-02-01')),
  PARTITION p202402 VALUES LESS THAN (UNIX_TIMESTAMP('2024-03-01')),
  ...
);
```

### 3. Оптимизация очистки логов

```sql
-- Использовать приблизительный подсчет
SELECT table_rows FROM information_schema.tables 
WHERE table_schema = 'monitoring' AND table_name = 'process_logs';

-- Или удалять по партициям
ALTER TABLE process_logs DROP PARTITION p202401;
```

### 4. Настройки MySQL для высокой нагрузки

```ini
[mysqld]
innodb_buffer_pool_size = 4G
innodb_log_file_size = 512M
innodb_flush_log_at_trx_commit = 2
innodb_flush_method = O_DIRECT
max_connections = 500
```

### 5. Увеличение интервала сбора данных

Для большого количества нод рекомендуется:
- COLLECT_INTERVAL=120 (2 минуты) вместо 60
- Логи собирать реже (раз в 5-10 циклов)

### 6. Использование репликации

- Master для записи (агенты)
- Slave для чтения (UI)
- Снижает нагрузку на основную БД

## Мониторинг производительности

Следить за:
- Время выполнения INSERT операций
- Количество блокировок таблиц
- Размер таблиц логов
- Время выполнения limitLogsCount()

## Вывод

**Для 50-100 нод:** текущая система работает адекватно
**Для 100-200 нод:** требуется оптимизация INSERT операций
**Для 200+ нод:** требуется партиционирование и репликация
